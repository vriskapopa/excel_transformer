Логика работы сервиса обработки документов и формирования Excel
Версия для финального подтверждения бизнес-логики
Цель документа
Документ фиксирует логику сервиса по двум переданным комплектам: «18233 ЛЮ 626 ТМЛ» и «BEIJING GOLDLUCK CO., LTD». Здесь описано, какие данные поступают, как они сопоставляются, что проверяется и какие файлы должны получаться. Конкретный интерфейс и способ программной реализации на этом этапе не фиксируются.
Ключевой принцип: система не просто меняет формат файла. Она собирает данные из нескольких документов, сопоставляет товарные позиции, дополняет сведения из согласованных справочников и баз, показывает расхождения и формирует готовые Excel-файлы.
1. Что уже подтверждено
За одну обработку сотрудник загружает все имеющиеся документы по поставке.
Система должна принимать как минимум Excel-файлы, PDF и сканы; сканы распознаются, а тип документа определяется автоматически.
Товарные позиции сопоставляются только по артикулу и/или модели. По смысловому сходству система товары не объединяет.
В системе должны быть поля для ручного заполнения шапки спецификации.
На первом этапе используются два переданных примера готовых Excel.
В комплекте BEIJING GOLDLUCK отмеченные заказчиком элементы таблицы не используются; остальные данные принимаются в обработку.
Три базы разрешительных документов на первом этапе используются отдельно и не объединяются в одну.
Зафиксировано: если значения в разных документах расходятся, система не выбирает одно из них незаметно, а показывает расхождение сотруднику для проверки.
2. Общая логика обработки
Сотрудник создаёт новую обработку (поставку) и загружает комплект файлов.
Система определяет тип каждого файла: инвойс, упаковочный лист, спецификация, справочник товаров, разрешительный документ или иной документ.
Из Excel данные считываются из таблиц. Для PDF и сканов выполняется распознавание текста и таблиц. Неуверенно распознанные значения помечаются для проверки.
Из документов формируется единая внутренняя таблица позиций.
Строки из разных документов связываются только по артикулу и/или модели. Допускается техническая нормализация регистра, пробелов и дефисов; неоднозначные совпадения не принимаются автоматически.
Коммерческие, упаковочные и классификационные данные объединяются в одну позицию. Отсутствующие сведения подставляются только из согласованного справочника или базы.
Система сравнивает повторяющиеся показатели между документами и подсвечивает пропуски, несовпадения, дубли, позиции без пары и результаты с низкой уверенностью распознавания.
Сотрудник проверяет результат, исправляет значения и вручную заполняет недостающие поля шапки.
После подтверждения система формирует редактируемый Excel по соответствующему образцу.
Состав единой позиции
идентификаторы: артикул, модель, дизайн, цвет;
коммерческие данные: количество, единица измерения, цена, сумма;
упаковочные данные: количество мест или рулонов, размеры, объём, метры, площадь, вес нетто и брутто;
классификационные данные: исходный HS code, итоговый таможенный код, русско-английское описание, страна и изготовитель;
разрешительные данные: вид и номер документа, статус, даты действия и применимость к товару — если этот блок входит в первую версию.

Дополнительные исходные документы в корневой папке:

Примечание: находящиеся в папке «Декларанту» страховка, счёт, CMR и PDF разрешительных документов являются частью контрольного комплекта. Из материалов не следует, что сервис должен автоматически создавать эти документы; ниже это вынесено на подтверждение.
3.3. Как собираются данные
Инвойс даёт модели/дизайны, HS code, количество рулонов, ширину, метры, площадь, цену и сумму.
Упаковочный лист даёт агрегированные данные по группам дизайнов: рулоны, метры, площадь, вес нетто и брутто.
Спецификация содержит детализацию по каждому рулону: номер рулона, дату, наименование, партию, метры, ширину, площадь и вес.
Система должна связать детальные строки спецификации с позициями инвойса, а затем сверить их с агрегатами упаковочного листа.
В готовый файл добавляются сведения шапки и классификационные данные, которых нет в исходных трёх таблицах. Источник этих добавочных данных должен быть однозначно определён.
3.4. Конкретный пример: Noble 110
В файле 626-1-YS-RMB-EXW-INVOICE.XLSX: 15 рулонов, 611,5 пог. м, 868,33 м², HS code 5407610000, цена 43,8 CNY за метр, сумма 26 783,70 CNY.
В файле 626-1-YS-RMB-EXW-PL.XLSX позиции Noble 110 и Noble 624 объединены в строку Noble: 27 рулонов, 1 118,5 м, нетто 1 062,58 кг, брутто 1 092 кг.
В готовом файле 18233 626-1 СПЕЦИФИКАЦИЯ С ЦВЕТАМИ.xlsx Noble 110 снова выделен отдельной строкой: 15 рулонов, 611,5 м, 868,33 м², нетто 580,93 кг, брутто 597,27 кг.
В готовом файле также появились двуязычное описание и таможенный код 5407613000, хотя в исходном инвойсе указан HS code 5407610000.
Следствие для логики: это не прямое копирование столбцов. Нужно разложить общий упаковочный показатель по моделям на основании детализации, проверить итоги и получить дополнительные классификационные сведения из заранее определённого источника.
4. Пример «BEIJING GOLDLUCK CO., LTD»
4.1. Файлы, которые поступают
(поступление)Invoice n Packing list（003-26E,20260703)-00.xlsx — исходные данные поставки; листы Invoice + Packing list и Packing list.
(описание )сводная.xlsx — справочник артикулов, кодов и двуязычных описаний; отмеченные заказчиком элементы не используются.
26BEETINT-001_signed.pdf — подписанный скан без поискового текстового слоя, поэтому для извлечения данных требуется распознавание.
Контрольный результат:
обработан с учетом данных (готов)для ЭД 18018.xlsx — листы Invoice, Packing list, Specification и описание.
4.2. Как собираются данные
Из исходного файла поставки берутся артикул, цвет, количество, единица измерения, цена, сумма, размеры упаковки, количество коробок, объём, вес нетто и брутто.
По артикулу/модели выполняется поиск в (описание )сводная.xlsx. При совпадении в результат подставляются таможенный код и двуязычное описание.
Если артикул отсутствует в справочнике, система не придумывает код и описание, а помечает позицию для ручного решения или поиска в другом согласованном источнике.
После проверки формируется один Excel с четырьмя листами по структуре готового образца.
4.3. Конкретный пример: MD 812
В исходном файле поставки: артикул MD 812, 200 100 шт., цена 0,0592 CNY, сумма 11 845,92 CNY.
В справочнике (описание )сводная.xlsx для MD 812 указаны код 7318230009 и описание Furniture metal rivet 8 x 12 mm… / Заклепка мебельная ступенчатая 8 × 12 мм…
В готовом файле эти сведения объединены: коммерческие и упаковочные показатели взяты из поставки, а код и описание — из справочника.
4.4. Исключения, которые система должна выявлять
Технические различия в написании, например MO SHO-01 / MOSHO-01 и VA04 / VA 04, можно нормализовать, поскольку сам артикул сохраняется.
Строка без артикула не должна автоматически присоединяться к соседней позиции — она помечается для проверки.
Артикулы MD 811, MD 821, MD 825, MD 828, MD 829, MD 832, MD 847, VA01, VA02 и D3.2-909 отсутствуют в переданном справочнике, но в готовом файле код и описание для них заполнены. Следовательно, использовался ещё один источник или ручная работа; это нужно зафиксировать.
5. Базы разрешительных документов
Переданы три самостоятельные базы:
ДС/РД ДС.xlsx
СС/РД.xlsx
От Сармант база РД/БАЗА_РД от 19.08(10).xlsx
На первом этапе базы не сливаются. Для каждой товарной позиции сервис обращается к ним отдельно и показывает, из какой базы получен результат.
Предлагаемая логика проверки
Отобрать возможные разрешительные документы по коду ТН ВЭД, изготовителю и, где данные присутствуют, модели/артикулу.
Сравнить наименование и полное описание продукции, торговую марку, изготовителя и страну.
Проверить статус документа и срок действия.
Показать сотруднику найденные варианты, несовпадения и отсутствие результата отдельно по каждой базе.
Окончательный выбор разрешительного документа подтверждает сотрудник.
Важно: точные совпадения кодов, моделей и дат проверяются обычными правилами. Нейросеть может помогать сравнивать длинные свободные описания товара и область действия разрешительного документа, но не должна единолично принимать юридически значимое решение.
6. Где требуется нейросетевая обработка
Нейросеть/OCR действительно нужна для:
распознавания сканов и PDF без текстового слоя;
определения типа документа и структуры таблицы, если форма поставщика меняется;
сопоставления названий столбцов в разных шаблонах;
предварительного сравнения длинного описания товара с областью действия разрешительного документа;
оценки уверенности и передачи спорных значений сотруднику.
Нейросеть не нужна для:
математических расчётов и сверки итогов;
точного поиска по артикулу/модели;
подстановки уже найденной строки из справочника;
формирования Excel по заранее утверждённому шаблону.
Поэтому оценка может быть небольшой только для узкого варианта: два фиксированных Excel-шаблона, без сканов, без новых форматов, без поиска дополнительных кодов и без разрешительных баз. Описанные материалы показывают более широкую логику.
7. Результат обработки
На закрытой странице сотрудник видит список загруженных файлов и распознанные типы документов.
До выгрузки доступна единая таблица позиций с пометками: пропуск, расхождение, позиция без соответствия, низкая уверенность распознавания, несколько вариантов разрешительного документа.
Сотрудник может исправить значения и заполнить поля шапки.
После подтверждения формируются редактируемые Excel-файлы по одному из двух согласованных профилей результата.
Ошибки не скрываются и не заменяются автоматически предположениями системы.
8. Что нужно подтвердить для финальной оценки
Остальная логика выше считается верной. Просьба подтвердить или скорректировать только следующие пункты:
Первая версия должна работать только с двумя переданными структурами файлов или сразу с произвольными Excel/PDF разных поставщиков без предварительной настройки?
Откуда система должна брать таможенный код, двуязычное описание, страну, изготовителя и данные РД, если их нет в исходных документах или в (описание )сводная.xlsx: из другой вашей базы, через ручной ввод либо через автоматический поиск? Если используется другая база, просьба указать её.
Правильно ли описана работа с тремя базами РД: искать в каждой отдельно, показывать подходящие варианты и статус/срок действия, а окончательный выбор оставлять сотруднику?
Данные из 26BEETINT-001_signed.pdf и аналогичных сканов должны не только распознаваться, но и участвовать в сверке с Excel?
Для 18233 сервис должен формировать три Excel-файла и файл 18233 … описание.pdf по каждому комплекту 626-1/626-2; для BEIJING — один Excel с четырьмя листами. Верно ли это?
Комплекты 626-1 и 626-2 загружаются одной поставкой, после чего система сама делит их по номеру инвойса, или сотрудник создаёт две отдельные обработки?
В первой версии достаточно ручных полей шапки или нужно сразу сохранять контрагентов, договоры и условия поставки для последующего выбора из списка?
После ответа на эти пункты объём первой версии можно оценить без недооценки и без включения лишних функций.
